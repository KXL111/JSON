CommGateway 流程框图

1. 系统启动

main() 做不依赖网络的初始化并创建 WDG / BD / TT / START；北斗、天通走串口，调度一开始就运行；只有终端任务 TERM 要等 START 把网络初始化好。

2. 终端任务 TERM 主循环

TERM 是终端 UDP socket 的唯一使用者：处理终端发来的请求，也负责把 BD / TT 交来的结果和收到的短报文组成 JSON 发给终端。

3. 北斗任务 BD 主循环

BD 独占北斗串口 USART6。收到的语句只更新数据；发报、读卡、刷新 SQ 都在每圈末尾按时间检查，不依赖收数据的节奏。

4. 串口收发：DMA 循环接收 + 环形缓冲区 / DMA 发送

以北斗为例（天通一样，换成 USART3 / DMA1）。接收不占 CPU，任务晚一点来读也不丢；发送启动后立即返回，任务照常运行。

5. 北斗短报文发送：42212 → TCQ → FKI → 42213

同一时间只有一条在途；后面的请求在 BD 队列（深度 2）里等，队列满时终端立即收到失败。

6. 北斗短报文接收：TCI → 42214

北斗任务只负责解码，JSON 由终端任务组；主动上报的 msg_id、taskid 是两个独立生成的标准 UUID。

7. SQ / status 计算（每 1 s）

update_signal() 先看串口有没有数据，再由 PWI 波束数和 GSS 卫星数合成 SQ。结果写进 dev_status，心跳 42202 直接取用。

8. 天通任务 TT 主循环

天通协议还没到。串口（RS232，USART3）、任务、看门狗、和终端之间的通道都已就绪，收到的数据按行打印在调试串口上。

9. 看门狗

两级：业务任务向 WDG 任务报平安，WDG 任务确认大家都活着才喂硬件狗 IWDG。
