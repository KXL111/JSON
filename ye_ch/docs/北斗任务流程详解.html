北斗任务流程详解

北斗（BD）任务从上电、读卡、算信号，到收发短报文的每一步：由哪个函数完成、判断条件是什么、失败时终端收到什么。代码行号以 ye_ch/Projects/CommGateway 为准（no_ch 是同一份代码去掉注释，逻辑一致）。第 13 节是"北斗能不能改用 USART2"的原理图核查。

读卡（ICR / ICP）和信号（PWI / GSS → SQ）是状态面，只更新状态表、由心跳带给终端；发报（TCQ / FKI）和收报（TCI）是数据面，经两个队列和终端任务交换消息。

1 启动

调度器启动前，在 main() 里（main.c:111）：

  1. dev_status_init()：状态表全部清零，bd.status = 1（离线），建互斥锁。
  2. term_init()：建 TERM 队列，4 × text_msg_t，约 13 KB。必须先建好，因为 BD 一启动就可能调用 term_post()。
  3. bd_init()：建 BD 队列，2 × text_msg_t。
  4. 创建 BD 任务。

进入 bd_task() 之后：

  1. wdg_register("BD") 向看门狗登记。登记时刻就算第一次喂狗，3 s 内必须进入主循环。
  2. serial_open(SERIAL_BD, 38400)：建二值信号量 → 开 DMA2 时钟 → GPIO 设为复用、推挽、上拉 → 接收 DMA 以循环模式启动 → 发送 DMA 只配置不使能 → USART 设为 8N1，打开收发 DMA 请求和 IDLE 中断 → 使能。只有堆不够建信号量时才会失败，失败后 configASSERT 停机，由看门狗复位。
  3. s_rx_at = now：断线判断从这一刻计时，所以上电后有 5 s 宽限期。
  4. next_icr、next_sq 初值都是 0，所以第一圈就发 ICR、刷新 SQ。

2 主循环（每圈最长约 20 ms）

for (;;) {
  ① wdg_feed(wdg);                                  // 报平安
  ② n = serial_read(≤256 B, 最多等 20 ms);
     bd_framer_feed() → 每切出一句调用 on_line() → 按类型分发
  ③ if (在途 && 过了 deadline)   finish_send(1, "BD no response (FKI timeout)");
  ④ if (!在途 && BD 队列取到请求) start_send(&s_req);
  ⑤ if (!s_card_ok && 到点)      query_card();     next_icr = now + 5 s
  ⑥ if (到点)                    update_signal();  next_sq  = now + 1 s
}
  • 收到的语句只更新数据。所有定时动作都在每圈末尾按 tick 判断，不依赖收数据的节奏。time_reached()（bd_task.c:134）用有符号差值比较，tick 回绕时也正确。
  • ③ 在 ④ 前面：同一圈里先结束超时的那条，再取下一条，保证同一时刻只有一条短报文在途。
  • 串口有数据时 serial_read 立即返回；没有数据最多睡 20 ms，期间可被 IDLE 中断唤醒。

3 接收链路：串口 → 断句 → 解析 → 分发

3.1 serial_read()（serial.c:307）

  • DMA 循环写入 s_bd_rx[4096]。写指针 head = 4096 − DMA 剩余计数（NDTR）；读指针 rx_tail 只有 BD 任务会移动。单写单读，不用加锁。
  • rx_copy() 遇到跨越缓冲区末尾的数据时分两段拷贝。
  • 读取顺序：先取一次；取不到就 xSemaphoreTake(rx_sem, 20 ms)，醒来后再取一次。
  • IDLE 中断（serial.c:380）：先读 SR、再读 DR 来清标志（顺带清掉溢出标志），然后 xSemaphoreGiveFromISR 唤醒任务。
  • 余量：38400 波特率约 3.8 KB/s，4 KB 缓冲能存约 1 s。任务每 20 ms 来读一次，这期间只到约 77 B。万一被覆盖，坏掉的语句会被校验和挡掉。
  • 每圈最多取 256 B（BD_RX_CHUNK）。

3.2 断句 bd_framer_feed()（bd_proto.c:85）

断句器状态存在 s_framer 里（line[4352] 加 len），跨两次读取保存。逐字节处理：

收到的字节处理
$缓冲已经以 *hh 结尾（设备没发换行）就先把上一句交出去；然后清空，开始新的一句。没收完的半句直接丢掉
还没遇到 $ 之前的字节丢弃
\r 或 \n交出当前这一句；只有一个 $（长度 ≤ 1）的不交
累计超过 4351 字节整句丢弃（没有日志）
其他字节追加到缓冲

一段数据处理完时，如果缓冲已经以 *hh 结尾，也会立即交出。这样 FKI 不用等到下一句来了才被处理。

3.3 on_line()（bd_task.c:575）

  1. 打印原文 BD: rx: ...（CFG_LOG_BD_RAW=1 时）。PWI、GSS 在 k_periodic 表里，只有 CFG_LOG_BD_PERIODIC=1 才打印。原文必须在解析之前打，因为 bd_parse 会原地改写这一行。
  2. bd_parse() 失败：打印 BD: bad sentence (checksum should be *XX, or bad format), dropped，然后丢弃。
  3. 解析成功：设 s_rx_at = now、s_rx_bytes_mark = s_rx_bytes。任何类型的有效语句都算"链路活着"。
  4. 查 k_handlers 表分发：PWI → on_pwi，GSS → on_gss，ICP → on_icp，FKI → on_fki，TCI → on_tci。其他类型（SNR、IBD、ACK、STA 等）直接忽略。

3.4 bd_parse()（bd_proto.c:161）

  1. 必须以 $ 开头。
  2. 如果有 *：把 $ 和最后一个 * 之间所有字节做 XOR，结果必须等于 * 后面的两位十六进制（大小写都认）。通过后把 * 改成 \0。没有 * 的语句不校验，照样接受。
  3. 语句头（第一个逗号之前）至少 4 个字符，取最后 3 个作为类型：不看发送方标识，BD、CC、GN 开头都能识别。
  4. 把每个逗号改成 \0，argv[i] 依次指向各字段，最多 32 个。argv[0] 对应协议表里的第 1 字段，下标 = 编号 − 1。
"$BDFKI,032025,TCQ,Y,0,0*77"  →  type "FKI", argc 5, argv = { "032025", "TCQ", "Y", "0", "0" }

4 读卡：ICR → ICP

发送：query_card()（bd_task.c:608）组出 $CCICR,0,00*68\r\n（16 字节）。s_card_ok 为 false 时每 5 s 发一次，上电第一圈就发。serial_write 的返回值没检查。

接收：on_icp()（bd_task.c:402）。字段少于 18 个时忽略，等下次重发。它不看 s_card_ok，之后再收到 ICP 也会照样更新。

5 信号：PWI、GSS → SQ、status

5.1 PWI 波束信息（bd_task.c:344）

$BDPWI,时间,旧体制波束数N,[N 组 × 3 个字段],新体制波束数M,[M 组 × 4 个字段]*hh

old = atoi(argv[1]);   idx = 2 + old × 3;   new = atoi(argv[idx]);
例：$BDPWI,012430.31,00,03,11,45,45,00,16,49,49,00,21,46,46,00*4B   →   old 0, idx 2, new 3
  • old 不在 0~16 或 idx 越界时不更新；new 不在 0~16 时也不更新。
  • 只用新体制波束锁定数。design.txt 原文写的是旧体制，但实测旧体制一直是 00，用它 SQ 会永远为 0，所以代码有意改成了新体制。

5.2 GSS 卫星信息（bd_task.c:376）

只取 argv[0]，即可用卫星数（0~14）。区域短报文模块不输出 GSS，这一路就一直没有数据。两路都通过 sig_update() 记录：计数限制到 0~255，同时记下收到时的 tick，并置 seen = true。

5.3 update_signal()（bd_task.c:658），每 1 s 一次

  1. 判断串口链路：link = (now − s_rx_at ≤ 5 s)。
  2. 每路折算成级数：sig_level() —— 从没收到过，或超过 5 s 没更新，返回 −1（这一路没数据）；否则返回 min(数量, 4)。
  3. 两路组合成 SQ：见下表。
  4. 串口不通时强制 SQ = 0。
  5. 定 status：串口不通为 2（异常）；否则 SQ > 0 为 0（在线），SQ = 0 为 1（离线）。
  6. 加锁写入 bd.sq、bd.status。有变化时打 BD: status a -> b (...)、BD: SQ a -> b (beams x, sats y)。
  7. 乱码提示：串口不通、但这期间其实有字节进来（s_rx_bytes != s_rx_bytes_mark）时，每 5 s 打一次 BD: N bytes received on serial but no valid sentence, check baud rate (38400) and wiring。完全没有字节进来时（线断、设备没电）不打。

6 发报：42212 → TCQ → FKI → 42213

6.1 终端侧（TERM 任务）

  1. handle_json() 收到 42212：取 msg_type；缺 msg_id 或 taskid 时各补一个 UUID；用报文里的 timestamp 校准本机时间。
  2. forward_text(DEV_BD)（term_task.c:314）取出 target_id（最多 23 字节）和 msg（\uXXXX 转义已还原成 UTF-8，最多 3071 字节）。
  3. bd_submit() 调用 xQueueSend(..., 0)：按值拷贝，不等待。
  4. 失败时立即回 42213、status 1，errormsg 为 missing or invalid target_id、missing msg or msg too long 或 device busy or not available（BD 队列满，即已有 1 条在途、2 条在排队）。
  5. 提交成功时只打日志 TERM: BD text task <id> -> <号码>, queued，不回复，等 BD 交回结果。

6.2 start_send()（bd_task.c:276）

只在"没有在途短报文、且从队列取到请求"时调用。

  1. 登记在途：s_pending.active = true，保存 msg_id / taskid，taskstate 设为（taskid，进度 0）。
  2. 检查、编码、组包、发送，任一步失败就调用 finish_send(1, 原因)（见下表）。
  3. 截止时刻 = now + 字节数 × 10 × 1000 / 38400 ms（串口发送时间）+ 10000 ms。计时从发完开始算；最长的 TCQ 约 4030 字节，发送约 1.05 s。
  4. 进度设为 50；日志 BD: TCQ task <id> -> <号码>, N bytes GBK, M bytes on serial，再加一行 BD: tx: $BDTCQ,...。
检查项失败原因（成为 42213 的 errormsg）

6.4 超时

主循环第 ③ 步：time_reached(now, deadline) 成立时调用 finish_send(1, "BD no response (FKI timeout)")。

6.5 finish_send()（bd_task.c:219）

  1. 组一条 TEXT_RESULT 消息：设备为 BD，带上 status；msg_id / taskid 取自 s_pending（也就是终端当初请求里的）；text 是失败原因。
  2. 调用 term_post()，最多等 100 ms。放不进去时打日志 terminal queue full, result ... lost。
  3. 打日志 BD: task <id> sent 或 BD: task <id> failed: <原因>。
  4. 清除在途标志（active = false），清空 taskstate。

TERM 任务收到后，在 handle_device_msg() 里调用 reply_status(42213, 原 msg_id, 原 taskid, status, 原因)。

7 收报：TCI → 42214

on_tci() 在 bd_task.c:509。TCI 的字段（3.md 表 12）依次是：发信方、收信方、频点、时间、编码类型、数据标识、通信数据。字段少于 7 个时忽略。

  1. 打日志 BD: TCI parsed: from A to B, freq F, time T, code type C, data N chars。
  2. 编码类型为 3（混编）时调用 bd_mixed_decode()，要求以 A4 或 a4 开头、总长度为偶数、其余全是十六进制字符、还原后不超过 2000 字节。满足就得到 GBK 字节；不满足就打日志 not valid mixed code (A4 + hex), used as plain text。
  3. 编码类型为 1 或 2，或者混编解码失败时，把数据原文当作 GBK / ASCII 文本。
  4. gbk_to_utf8() 转成 UTF-8：结果最多 3071 字节，截断时落在完整字符边界上；查不到的码和孤立的高字节都换成 ?。
  5. 组一条 TEXT_RECV 消息：peer 填发信方号码，msg_id / taskid 留空，调用 term_post()。
  6. TERM 任务生成两个互相独立的 UUID，发出 42214。终端回的 42215 只打日志，不重发。本机不会向北斗模块回送任何收报确认。

8 编码规则（发和收对称）

发：UTF-8 ──gbk_from_utf8()──> GBK ──bd_mixed_encode()──> "A4" + 每字节两位大写十六进制
收："A4…" ──bd_mixed_decode()──> GBK ──gbk_to_utf8()──> UTF-8
例："12一二" ⇄ GBK 31 32 D2 BB B6 FE ⇄ "A43132D2BBB6FE"
  • gbk_from_utf8()：ASCII 原样写 1 字节；其他字符在升序表里二分查找，写 2 字节，高字节在前；emoji、查不到的字、非法 UTF-8 都换成 ?。
  • gbk_to_utf8()：首字节 0x81~0xFE 且尾字节 0x40~0xFE 的按双字节直接下标查表；其余高字节换成 ?。
  • 为什么用混编：汉字方式（类型 1）把 GBK 字节直接放进语句，正文里的逗号、*、$ 会破坏格式；代码方式（类型 2）只能发 0~9、A~F；混编全是十六进制文本，什么内容都安全。

9 状态总表与心跳里的 BD 字段

dev_status（dev_status.h）由 BD 任务加锁写，TERM 任务用 dev_status_read() 拷一份快照组心跳 42202。

11 看门狗

BD 每圈调用一次 wdg_feed。WDG 任务每 500 ms 检查一次，任何登记过的任务超过 3 s 没报平安，就停止喂硬件狗；停喂后 IWDG 约 4 s 溢出复位（LSI 时钟有偏差，实际在 2.7~7.5 s 之间）。

BD 单圈阻塞来源最长时间
等串口数据20 ms
等串口上一包发完1.5 s
term_post 等队列100 ms
日志阻塞发送（115200 下 1 KB 约 90 ms）最长报文约 0.5 s

都在 3 s 以内。复位后开机第一行日志会打印原因（watchdog / software / power on / reset pin）。

13 串口选择：北斗能不能改用 USART2

结论先说：板上 USART2 那个接口不是 RS422，而且它的 TX 脚和网口共用，接不了北斗；如果只是想换个 USART 编号，USART2 还能映射到 PD5 / PD6，但照样要外接 RS422 模块，和现在的 USART6 相比没有好处。以下依据都来自 refer/Explorer STM32F4_V2.2_SCH.pdf。

13.1 原理图上 USART2 接了什么

MCU PA2 ──┬── ETH_MDIO（LAN8720A 管理接口）     ← 同一个网络，PA2 被网口占用
          └── USART2_TX ──┐
MCU PA3 ──┬── PWM_DAC                          ← 同一个网络
          └── USART2_RX ──┤
                          P9 跳线（2×3）
                 ┌────────┴────────┐
          1-3、2-4 短接        3-5、4-6 短接
                 │                 │
           SP3232（RS232）     SP3485（RS485，方向脚 RS485_RE = PG8）
                 │                 │
           COM2（DB9）        RS485 端子（A、B 两根线，120Ω 终端电阻）
问题说明
没有 RS422 芯片整张原理图只有 SP3232（RS232）和 SP3485（RS485），没有 RS422 收发器。北斗 HBD4200 是 RS422，现在也是靠外接 TTL 转 RS422 模块
RS485 ≠ RS422SP3485 是 2 线半双工：一对 A/B 线，同一时刻只能一个方向，要用 PG8 切换收发。RS422 是 4 线全双工：收、发各一对线。北斗每秒主动输出 PWI，本机发 TCQ 时两边会在同一对线上撞车；代码也没有方向控制
RS232 电平不对COM2 是 ±5~15 V 的 RS232 电平，和 RS422 差分电平不兼容，不能直接接
PA2 是网口 MDIO原理图上 PA2 这个网络同时标着 ETH_MDIO 和 USART2_TX。ethernetif.c 开机时要用 MDIO 复位 PHY、等链路、读协商结果，没插网线时还会反复读。PA2 改成 USART2 发送脚，网口就初始化不了

13.2 各候选串口对比

串口引脚板上还接了什么能否接北斗 RS422
USART6（现用）PC6 发 / PC7 收（AF8）P4 排针引出；另连摄像头 P8 的 D0 / D1、WM8978 的 MCLK（本工程都不用，摄像头不要插）可以 外接 TTL 转 RS422 模块，和网口、调试口、天通都不冲突
USART2 默认PA2 发 / PA3 收（AF7）PA2 = ETH_MDIO；PA3 = PWM_DAC；经 P9 接 SP3232 / SP3485不行 见 13.1
USART2 重映射PD5 发 / PD6 收（AF7）PD5 = FSMC_NWE（接 SRAM 写使能、LCD 的 WR）；PD6 引到 IO 排针能用但没必要 同样要外接 RS422 模块；还要把 SRAM、LCD 片选拉高，免得 PD5 的跳变被当成写信号
USART3（天通在用）PB10 / PB11（AF7）P10 跳线接 SP3232，从 COM3 出 RS232已占用
建议保持 USART6。不管用哪个 USART，北斗的 RS422 都要外接 TTL 转 RS422 模块；USART6 在 P4 排针上直接引出、没有任何冲突，是这块板上最干净的选择。

14 读代码时发现的注意点

都还没改，改法见 调试与扩展 第 8 节。

  1. 迟到的 FKI 可能被算到下一条头上（bd_task.c:477）。on_fki() 只看有没有在途，不核对回执属于哪一条（FKI 里也没有任务号）。A 超时后 B 立刻发出，A 的 FKI 晚到就被当成 B 的结果；B 自己的 FKI 再到时被丢弃。模块正常约 1 s 回执，只在响应异常慢时出现。
  2. 文档和代码不一致：北斗协议语句详解.html 的 FKI 一节说"由此维护 bd_fki"，代码里没有 bd_fki。等待秒数只拼进 errormsg，本机不按 CD 主动节流，频度未到时靠模块拒绝。
  3. TCI 混编数据过长时上报十六进制原文（bd_task.c:521）。还原后超过 2000 字节时解码失败，退回"当文本处理"，终端收到一串 A4…。
  4. 超长语句被丢弃时没有日志（bd_proto.c:104）。
  5. ICR 发送失败感知不到（bd_task.c:613）：日志照样打 "query card"。5 s 后会重发，影响只是日志不准。
  6. 卡信息只读一次：运行中换卡或权限变化，要重启才生效。
  7. 终端用 \uXXXX 转义发满 1000 个汉字时可能被截断：JSON 约 6.1~6.2 KB，接近或超过 TERM_RX_MAX（6144）。直接发 UTF-8（约 3 KB）没问题。
  8. 没有 *hh 的语句不校验就接受（bd_proto.c:172），这类语句同样会刷新"链路活着"的时间。
